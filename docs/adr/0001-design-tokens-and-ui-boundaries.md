# ADR 0001：设计 tokens 与 UI 职责边界

- 日期：2026-09-07
- 状态：已采纳，分阶段实施
- 范围：桌面应用 src/；不包含 website、Rust 后端和文档自带样式

## 背景

应用使用 React、Tailwind 和 Tauri。readerTheme.ts 已提供五种阅读主题，但组件仍包含独立的色值与深浅模式判断。应用界面直接使用 gray、slate、blue 等颜色类。SettingsUI 已有局部复用基础；ReaderContent、Library 和 Settings 同时承担较多职责。

## 决策

1. 以 CSS 自定义属性作为应用视觉 tokens 的运行时来源，并在 Tailwind 中映射语义名称。保留现有 Tailwind 间距、字号、圆角、阴影尺度；不机械地为每个工具类再造变量。
2. 区分基础尺度、语义 tokens 和按需引入的组件 tokens。颜色用用途命名，例如 surface、foreground、action、border，不以当前色值命名。
3. 应用界面主题与阅读主题分别作用于各自容器。保留 white/paper/mint/sepia/night 标识、设置存储键和用户偏好兼容性。第一批仅建立当前浅色应用主题，不默认新增全局夜间模式。
4. 用户字号、行距、栏宽和拖拽几何属于运行时输入，可通过 inline style 或 CSS 变量传递。百分比、零值、布局结构、第三方 KaTeX 和文档固有样式属于明确例外。
5. “100% tokenized”指范围内所有产品视觉决策都引用统一规则，且例外可解释；不指删除一切 CSS 字面量。迁移中的旧代码以计划记录，不宣称全量完成。
6. 公共 UI 放在 components/ui；业务组件逐步按 features/library、reader、settings、ai-tools 组织。先按职责识别边界，再迁移；不按行数强制切文件。
7. 样式迁移与复杂业务逻辑拆分分批验收。第一批保持现有视觉和行为，迁移 SettingsUI 作为试点；后续逐页推广。
8. 对已迁移边界提供自动样式检查，阻止新增直接调色板类、原始色值和未登记的任意视觉数值。每批扩大检查范围。

## 替代方案

- 全部改用 CSS Modules：无法单独解决设计决策分散问题，并增加无必要的语法迁移。
- 所有数字都变成 tokens：会混淆布局计算和设计规则，制造大量无复用意义的名称。
- 一次性改写全部组件：视觉与功能回归难以定位。

## 影响

主题与控件状态获得统一入口；迁移期间新旧样式暂时共存。新增语义必须有明确用途，避免 token 名称无限增长。公共组件仅抽取稳定重复模式，不把阅读业务逻辑放入 UI 基础层。

## 验收

每批通过样式检查、TypeScript 和生产构建；完成对应页面的视觉及交互验证。最终覆盖五种阅读主题、正文/代码/译文/批注、双栏、字号行距栏宽设置与核心阅读流程。没有实际运行的检查必须明确标注。
